# UI-сценарії для Selenium WebDriver — Спринт 4

**Продукт:** «ШопЛайн» / demo Toolshop  
**Базова URL:** `https://practicesoftwaretesting.com`  
**Джерело:** тест-кейси Sprint 3 (`test-cases.xlsx`) та SRS-1.1.  
**Призначення:** специфікація для реалізації 6 стабільних UI-тестів Selenium WebDriver 4 у пакеті `ui`.

## Загальні правила реалізації

- Кожен сценарій — окремий незалежний тест, який створює власний стан.
- Використовувати Chrome з `--headless=new`, `--window-size=1280,900` і `WebDriverWait` до 15 секунд. Не використовувати `Thread.sleep`.
- Позначити тест-клас/методи `@Tag("ui")`; запуск повного набору: `mvn test -DexcludedGroups=none`.
- Створювати браузер у `@BeforeEach`, обов'язково викликати `driver.quit()` у `@AfterEach`.
- Пріоритет локаторів: унікальний `id` або `data-test`. До реалізації перевірити кожен локатор у DevTools → Elements (`Ctrl+F` має показати `1 of 1`). Якщо демо змінило розмітку, записати фактичний `id`/`data-test` з поточного DOM, а не підставляти вигаданий селектор.
- Не використовувати реальні платіжні дані. Ці сценарії не виконують оплату.
- Для входу використовуються навчальні дані з SRS-1.1: `customer@practicesoftwaretesting.com` / `welcome01`. Для негативного входу використовується неправильний пароль `WrongPass!2026`.

## UI-04 — Додавання одного товару до кошика (quantity = 1)

| Поле | Значення |
|---|---|
| **Тест-кейс Sprint 3** | `TC-012`, набір даних `qty=1` |
| **Вимога** | `F-90`, `GUI-30`, `GUI-70` |
| **Тип / пріоритет** | Позитивний / High |
| **Передумови** | Нова сесія браузера; кошик порожній; користувач не авторизований; доступний щонайменше один товар у наявності. |
| **Тестові дані** | Кількість `1`; перший товар у наявності (його назву прочитати з картки під час виконання). |

| Крок | Дія та локатор | Очікувана перевірка |
|---:|---|---|
| 1 | Відкрити `BASE_URL`; дочекатися клікабельної картки `a[data-test^='product-']` і відкрити товар у наявності. | Відкрита сторінка товару; назва доступна через `[data-test='product-name']`. |
| 2 | Знайти поле `Quantity` за його фактичним унікальним `id`/`data-test` у DevTools та встановити `1` (перевірити селектор перед реалізацією). | Поле показує `1`. |
| 3 | Дочекатися клікабельності `[data-test='add-to-cart']` і натиснути. | Кошик оновлюється; `[data-test='cart-quantity']` показує `1` (або відповідний лічильник у поточному DOM). |
| 4 | Відкрити кошик за фактичним `data-test` локатором навігації та дочекатися таблиці позицій. | У кошику один рядок; назва збігається з назвою товару з кроку 1, кількість дорівнює 1. |

**Рекомендований `@DisplayName`:** `TC-012 / F-90: add one item updates cart count and row`.

## UI-05 — Додавання максимальної допустимої кількості (quantity = 99)

| Поле | Значення |
|---|---|
| **Тест-кейс Sprint 3** | `TC-012`, набір даних `qty=99` |
| **Вимога** | `F-90`, `GUI-30` |
| **Тип / пріоритет** | Позитивний, граничне значення / High |
| **Передумови** | Нова сесія; кошик порожній; доступний товар у наявності. Цей тест запускається в окремому браузері від UI-04. |
| **Тестові дані** | Кількість `99`; товар у наявності. |

| Крок | Дія та локатор | Очікувана перевірка |
|---:|---|---|
| 1 | Відкрити `BASE_URL`, відкрити товар у наявності через `a[data-test^='product-']`. | Сторінка товару видима; лічильник кошика дорівнює 0 або відсутній. |
| 2 | Поле `Quantity` знайти за перевіреним `id`/`data-test`, очистити та ввести `99`. | Поле відображає `99`; значення не обрізається до меншого числа. |
| 3 | Натиснути `[data-test='add-to-cart']` після `elementToBeClickable`. | Товар додається; лічильник кошика дорівнює `99`. |
| 4 | Відкрити кошик, дочекатися таблиці позицій. | Один рядок товару з кількістю `99`; сторінка не створює зайвих рядків для того самого товару. |

**Примітка:** SRS визначає діапазон 1–99. Не додавати в цей сценарій значення 100: воно перевіряється негативним ручним кейсом `TC-013`, який у Sprint 3 пов'язувався з реальним дефектом і може навмисно зробити тест червоним на поточному demo.

**Рекомендований `@DisplayName`:** `TC-012 / F-90: quantity 99 is accepted at the upper boundary`.

## Локатори, які потрібно підтвердити в DevTools перед написанням коду

| Елемент | Локатор із методички / кандидат | Дія |
|---|---|---|
| Email для входу | `By.id("email")` | Перевірити у DOM, що знайдено один видимий елемент. |
| Password для входу | `By.id("password")` | Перевірити у DOM, що знайдено один видимий елемент. |
| Login submit | `[data-test='login-submit']` | Перевірити у DOM. |
| Search input | `[data-test='search-query']` | Перевірити у DOM. |
| Search submit | `[data-test='search-submit']` | Перевірити у DOM. |
| Product link/card | `a[data-test^='product-']` | Перевірити, що це посилання на товар і воно доступне для натискання. |
| Product name | `[data-test='product-name']` | Після пошуку дочекатися, поки всі назви відповідають `hammer`. |
| Add to cart | `[data-test='add-to-cart']` | Перевірити на сторінці товару. |
| Cart quantity/count | `[data-test='cart-quantity']` | Перевірити, що це потрібний лічильник (не кількість окремого рядка). |
| Quantity input на сторінці товару | Фактичний `id` або `data-test` з поточного DOM | **Не вигадувати атрибут**: знайти поле за видимою назвою `Quantity` у DevTools і записати реальний локатор. |
| Search clear (X) | Фактичний `id` або `data-test` з поточного DOM | **Не вигадувати атрибут**: перевірити кнопку очищення. |
| Login error | Фактичний `data-test` повідомлення помилки | Зафіксувати локатор і точний текст повідомлення при ручному прогоні. |
| Contact nav / submit | `[data-test='nav-contact']`, `[data-test='contact-submit']` | Перевірити у поточному DOM; поля форми — `first_name`, `last_name`, `email`, `subject`, `message`. |
