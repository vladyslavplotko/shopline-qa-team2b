## Частина 1. Чек-листи перевірки BPMN-моделей

### 1. Модель `01_zamovlennya.drawio.png` (Процес замовлення)

| № | Пункт чек-листа | Так / Ні | Зауваження |
|---|---|:---:|---|
| **1** | Кожен процес має щонайменше одну початкову і одну кінцеву подію; немає дій без вхідного або вихідного потоку | **Так** | Кожна доріжка має чіткі стартові та фінальні події, ізольованих дій немає. |
| **2** | Учасники відображені пулами, підрозділи або ролі всередині організації — доріжками; кожна дія лежить у доріжці свого виконавця | **Так** | Чітко розділено пули «Покупець» та «Shopline» (доріжки: Сайт, Менеджер магазину). |
| **3** | Потоки керування не перетинають межі пулів; взаємодія між пулами показана потоками повідомлень | **Так** | Між пулами використовуються виключно пунктирні потоки повідомлень (Message Flows). |
| **4** | Кожен шлюз, що розгалужує, має умови на вихідних потоках (або позначений потік за замовчуванням); тип шлюзу (ексклюзивний, паралельний, інклюзивний, за подіями) відповідає логіці | **Так** | Шлюзи перевірки авторизації, способу оплати та наявності товару мають підписані гілки («Увійшов», «Картка», «Ні» тощо). |
| **5** | Паралельне розгалуження закрите парним шлюзом того самого типу; немає «висячих» гілок | **Так** | Паралельні гілки правильно зводяться/закриваються без «висячих» елементів. |
| **6** | Назви дій — дієслово + об'єкт («Перевірити наявність товару»), назви подій — стан («Замовлення оплачено») | **Так** | Дії сформульовані дієсловами («Ввести дані карти», «Сформувати рахунок»), події — станами. |
| **7** | Проміжні події (таймер, повідомлення, помилка) використані там, де процес чекає або реагує на зовнішню подію | **Так** | Використано проміжні події таймера (наприклад, очікування 24 години) та повідомлень. |
| **8** | Артефакти даних (об'єкти даних, сховища) та анотації присутні там, де вони пояснюють, з чим працює дія | **Так** | Наявне сховище даних/база даних та об'єкт даних «Рахунок». |
| **9** | Підпроцеси використано для повторюваних або складних фрагментів; діаграма читається без пояснень автора | **Так** | Використано згорнутий підпроцес «Комплектація і відправлення» у доріжці Менеджера. |
| **10** | Модель відповідає легенді продукту: учасники, кроки й рішення узгоджені з описом процесу в каталозі; альтернативні й помилкові сценарії (відмова, скасування) показані | **Так** | Відображено як успішне оформлення, так і скасування/відмову (товар відсутній, помилка оплати). |

## Частина 2. Чек-лист перевірки якості User Stories (US-01 ... US-12)

| № | Критерій якості | Статус | Зауваження |
|---|---|:---:|---|
| **1** | **Формат "Як [роль] я хочу [дія] щоб [мета]"** | **Так** | Усі 12 сторіс чітко дотримуються канонічної структури (Роль, Бажання, Мета). |
| **2** | **Атомарність та незалежність (Independent)** | **Так** | Кожна сторіс описує окрему функцію (наприклад, US-03 — введення, US-10 — видалення промокоду). |
| **3** | **Адаптивність / можливість обговорення (Negotiable)** | **Так** | Описано сутність бажаного результату без жорсткої прив'язки до деталей реалізації коду. |
| **4** | **Цінність для користувача/бізнесу (Valuable)** | **Так** | Кожна сторіс містить чітко сформульовану бізнес-мету в колонці «Мета». |
| **5** | **Можливість оцінки (Estimable)** | **Так** | Обсяг робіт зрозумілий, вимоги не містять двозначностей для розробників. |
| **6** | **Компактність / розмір (Small)** | **Так** | Функціонал розбито на невеликі ітеративні кроки (наприклад, налаштування та перегляд логів розділені). |
| **7** | **Тестованість (Testable)** | **Так** | Примітки містять чіткі граничні умови та тестові сценарії (формат, межі 1..50%, логічні перевірки). |
| **8** | **Повнота покриття вимог замовника** | **Так** | Усі 6 очікувань замовника з матриці відстежуваності повністю перекриваються сторісами US-01...US-12. |
| **9** | **Пріоритеризація** | **Так** | Для кожної сторіс проставлено бізнес-пріоритет (High / Med / Low) за методологією MoSCoW. |
| **10** | **Наявність негативних та крайніх сценаріїв** | **Так** | Вказано перевірки для від'ємних балансів, прострочених кодів, порожніх списків та некоректних вводів. |

## Підсумковий висновок
1. **BPMN-моделі:** Процеси `01_zamovlennya` та `03_zvernennya` відповідають вимогам на 100%. У моделі `02_povernennya` рекомендовано за бажанням додати графічний об'єкт даних «Заява на повернення».
2. **User Stories:** Беклог вимог (US-01 — US-12) повністю відповідає критеріям якості та на 100% покриває 6 очікувань замовника.
